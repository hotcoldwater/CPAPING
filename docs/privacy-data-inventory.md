# CPAPING 개인정보 처리 현황

법률 자문용 사실 정리. 방침 초안이 아니라 **실제 구현이 무엇을 어떻게
처리하는지**를 코드와 DB 스키마에서 확인해 적은 것이다.

- 작성일: 2026-08-31
- 서비스: https://cpaping.com (운영 중, 아직 홍보 전 · 구독자 0명)
- 소스: https://github.com/hotcoldwater/CPAPING (public)

---

## 1. 서비스 개요

한국공인회계사회(한공회) 웹사이트의 **구인(수습CPA) 게시판**을 10분 간격으로
조회해 새 채용 공고를 수집하고, 구독자에게 이메일로 알린다.

- 이용자: 공인회계사 시험 합격자·수습 회계사 (성인)
- 수익 모델: 없음 (무료, 광고 없음)
- 회원가입·로그인: **없음.** 이메일 구독만 있다

## 2. 수집하는 개인정보

### 2.1 이용자에게서 직접 수집

| 항목 | 필수 여부 | 수집 시점 | 비고 |
|---|---|---|---|
| **이메일 주소** | 필수 | 구독 신청 시 | 유일한 수집 항목 |

### 2.2 서비스가 생성·저장하는 부수 정보

| 컬럼 | 내용 |
|---|---|
| `email_normalized` | 이메일을 소문자로 바꾼 값. 대소문자만 다른 중복 신청 방지용 |
| `confirm_token` | 구독 확인 링크용 난수(48자리 16진수) |
| `unsubscribe_token` | 수신 거부 링크용 난수(48자리 16진수) |
| `employment_filter` | `all` / `full`(정규직) / `part`(파트타임). 어떤 공고를 받을지 |
| `status` | `pending`(확인 대기) / `active`(구독 중) / `unsubscribed`(해지) |
| `created_at` | 신청 시각 |
| `confirmation_sent_at` | 확인 메일 발송 시각 |
| `confirmed_at` | 구독 확정 시각 |
| `unsubscribed_at` | 해지 시각 |

별도 테이블 `notification_logs` 에 **어떤 구독자에게 어떤 공고를 언제 보냈는지**
기록한다(중복 발송 방지 목적). 구독자 ID·공고 ID·발송 시각만 저장한다.

### 2.3 수집하지 않는 것

명시적으로 수집하지 않는다.

- 이름, 생년월일, 전화번호, 주민등록번호, 주소
- 접속 IP 주소, 접속 기록, 방문 이력
- **쿠키를 사용하지 않는다.** 접속 통계 분석 도구(Google Analytics 등)도 설치하지 않았다

> 다만 브라우저의 `localStorage` 에 화면 설정 두 가지를 저장한다
> (`cpaping.filter`, `cpaping.sort` — 목록 필터와 정렬 순서).
> 개인을 식별할 수 없는 값이며 서버로 전송되지 않는다.

## 3. 처리 흐름과 각 단계에서 이메일이 지나는 곳

```
① 구독 신청
   브라우저 → Cloudflare Pages Functions → Supabase(저장)
                                        → Resend(확인 메일 발송)

② 구독 확정
   확인 메일의 링크 클릭 → Cloudflare Pages Functions → Supabase(상태 변경)

③ 공고 알림
   Cloudflare Worker(정시 트리거) → GitHub Actions(크롤러 실행)
      → Supabase(구독자 목록 조회) → Google Gmail SMTP(발송)

④ 해지
   메일 하단 링크 클릭 → Cloudflare Pages Functions → Supabase(상태 변경)
```

**③에서 GitHub Actions 가 구독자 이메일 주소를 읽어 처리한다.** 크롤러(Python)가
GitHub 의 가상 머신에서 돌면서 Supabase 에서 구독자 목록을 가져와 메일을 보낸다.
저장하지는 않지만 처리 과정에서 거친다.

## 4. 처리 위탁 및 국외 이전

모든 수탁자가 국외 사업자다.

| 수탁자 | 국가 | 위탁 업무 | 이전 항목 | 보관 여부 |
|---|---|---|---|---|
| **Supabase Inc.** | 미국 | 데이터베이스 | 이메일, 토큰, 상태, 시각 | 보관 |
| **Cloudflare, Inc.** | 미국 | 웹 호스팅, 구독 신청 처리, 트리거 | 이메일(전달만) | 미보관 |
| **Resend, Inc.** | 미국 | 확인 메일 발송 | 이메일 | 발송 이력 보관(사업자 정책) |
| **Google LLC** | 미국 | 공고 알림 메일 발송(Gmail SMTP) | 이메일 | 발송 이력 보관 |
| **GitHub, Inc.** (Microsoft) | 미국 | 크롤러 실행 환경 | 이메일(처리만) | 미보관 |

- **Supabase 데이터베이스 리전: 서울(`ap-northeast-2`)** — 2026-08-31 대시보드에서 확인.
  **데이터 자체는 국내에 저장된다.** 다만 Supabase 는 미국 법인이므로
  본사에서의 접근 가능성 때문에 국외 이전으로 볼 여지가 있다. 이 점이
  고지·동의 요건에 영향을 주는지 자문이 필요하다(8항 3번 질문).
- 이전 방법: 서비스 이용 시 정보통신망을 통한 전송

## 5. 보유 및 파기 — ⚠️ 현재 구현과 방침이 어긋날 수 있는 지점

**현재 코드에는 개인정보를 자동으로 삭제하는 로직이 없다.**

| 상황 | 현재 동작 | 검토 필요 |
|---|---|---|
| 이용자가 **해지**한 경우 | `status` 를 `unsubscribed` 로 바꾸고 **이메일 주소는 그대로 남긴다** | 즉시 파기해야 하는가? 재가입 방지 목적 보관이 허용되는가? |
| 확인 메일을 받고 **끝내 확인하지 않은 경우** | `pending` 상태로 **무기한 남는다** | 일정 기간 후 자동 삭제가 필요한가? |
| 발송 이력(`notification_logs`) | 구독자 삭제 시 함께 삭제됨(외래키 cascade) | 별도 보존 의무가 있는가? |

해지자의 이메일을 남겨둔 이유는 없다 — 단지 구현하지 않았을 뿐이다.
**자문 결과에 따라 다음 중 하나로 정리할 예정이다.**

1. 해지 시 행 전체 삭제 (가장 단순)
2. 이메일을 지우고 해시만 남겨 재가입·수신거부 이력만 유지
3. 일정 기간(예: 30일) 후 자동 삭제

## 6. 제3자(채용 담당자) 개인정보

한공회 공고 원문에는 채용 담당자의 **이름·전화번호(개인 휴대폰 포함)·이메일
주소(개인 Gmail 포함)** 가 적혀 있다.

- **2026-08-31 자로 수집을 중단했다.** DB 컬럼도 삭제했고, 이미 저장돼 있던
  17건의 값도 지웠다
- 현재는 법인명·법인 홈페이지 등 법인 정보만 저장한다
- 알림 메일에도 담당자 연락처를 싣지 않는다. 이용자는 **한공회 원문 링크**를
  통해 직접 확인한다

수집한 공고 정보: 제목, 회사명, 지역, 고용형태, 마감일, 등록일, 본문, 원문 링크

## 7. 안전성 확보 조치

- **행 수준 보안(RLS)**: 구독자 테이블에 RLS 를 켜고 접근 정책을 두지 않았다.
  웹사이트에 공개된 키로는 구독자 정보를 **읽을 수도 쓸 수도 없다**(실제 요청 시 401).
  채용 공고만 읽기 가능하다
- **키 분리**: DB 전체 권한을 가진 키는 서버(Cloudflare Functions, GitHub Actions)
  에서만 쓰고 브라우저로 나가지 않는다. 소스 코드에 포함하지 않고 각 플랫폼의
  암호화된 환경변수로 관리한다
- **전 구간 HTTPS**
- **구독 신청 서버 경유**: 브라우저에서 DB 로 직접 쓰지 못하게 해 스크립트를 통한
  대량 등록을 막았다
- **더블 옵트인**: 본인이 링크를 눌러야 구독이 확정된다. 타인의 주소를 함부로
  등록할 수 없다
- **원클릭 해지**: 재확인 절차 없이 링크 한 번으로 해지된다.
  `List-Unsubscribe` 헤더도 넣어 메일 클라이언트의 해지 버튼도 동작한다

## 8. 자문에 여쭙고 싶은 것

1. **해지자의 이메일 주소를 보관해도 되는가?** 재가입·수신거부 이력 관리 목적으로
   보관이 허용된다면 기간은? 아니면 즉시 파기해야 하는가? (5항 참조)
2. **확인하지 않은 신청(`pending`) 건의 보유 기간**을 어떻게 정해야 하는가?
3. **국외 이전에 별도 동의**가 필요한가, 처리방침 공개와 고지로 충분한가?
   수탁자 5곳이 모두 미국 사업자이지만, **데이터베이스는 서울 리전에 저장**된다.
   저장 위치가 국내면 국외 이전이 아닌 것으로 볼 수 있는가, 아니면 사업자
   소재지를 기준으로 보아야 하는가?
4. 채용 공고 알림이 **정보통신망법상 영리목적 광고성 정보**에 해당하는가?
   해당한다면 제목의 `(광고)` 표기, **2년마다 수신동의 여부 확인** 의무 등이
   따라오는지 확인이 필요하다. 서비스는 무료이고 광고·수익이 없다
5. **개인정보 보호책임자**를 지정해야 하는가? 개인이 운영하는 무료 서비스인데
   실명·연락처를 공개해야 하는 범위는?
6. **만 14세 미만** 확인 절차가 필요한가? 실질 이용자는 공인회계사 시험 합격자라
   미성년자가 사실상 없다
7. 한공회 게시판의 **공고 정보를 수집·재가공해 제공**하는 것에 법적 문제가 있는가?
   (원문 전재가 아니라 요약과 원문 링크만 제공한다. `robots.txt` 는 전체 허용)
8. 사업자등록 없이 개인이 운영할 때 **이용약관**도 필요한가?
