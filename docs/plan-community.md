# 커뮤니티·자소서 계획 (의견, 2026-09-09)

> 2026-09-11부터 실행 순서·변경 정책·진행 상태는 [성장 실행 로드맵](growth-roadmap.md)이 기준이다.
> 이 문서는 기존 설계와 결정의 기록으로 유지한다.

운영자의 목표는 **준비생·합격생·현직자(회계법인·사기업)가 소통하는 회계사 커뮤니티**다.
공고 알림과 법인 DB는 그 입구다. 아래는 게시판·댓글·인증·자소서를 어떤 순서와 구조로
붙일지에 대한 의견이다. **결정된 것과 제안을 구분해 적는다.**

## 결정된 것 (운영자)

- 공고 상세 페이지에 원문 전문은 싣지 않는다 (배포 완료)
- 댓글은 닉네임 표시, 가입만 하면 가능(자격 인증 없음), 익명 불가
- 탈퇴해도 댓글·글은 남기고 "탈퇴한 사용자"로 익명화
- 법인 댓글은 이용약관 뒤로 → 약관 제1판 배포(`/terms`) 뒤 2026-09-09 법인 댓글 배포 완료
- 로그인: 구글·이메일 가입 배포. 카카오(개인 개발자 앱은 이메일 scope 불가, KOE205)·네이버는 나중에 함께
- 뱃지: 합격자는 **기수**(합격연도 − 1965, 2026 = 61기), 법인 소속, 공식 계정
- 인증 자료: 합격사실확인서 또는 한공회 등록명부, 성명 가운데 글자만·주민번호 삭제, 확인 즉시 파기

## 1. 회원의 세 부류와 뱃지

| 부류 | 뱃지 | 확인 방법 | 비용 |
|---|---|---|---|
| 준비생 | `준비생` | **자기 선택**(가입 시 "나는 준비생") — 인증 없음. 뱃지가 아니라 프로필 표시에 가깝다 | 0 |
| 합격생 | `합격자 · 61기` | 합격사실확인서 수동 심사 | 건당 수동 |
| 등록 회계사 | `회계사` | 한공회 등록명부 수동 심사 | 건당 수동 |
| 회계법인 현직 | `법인 소속 · OO회계법인` | 로그인 이메일 도메인 자동 / 등록명부의 사무소명 / 재직 자료 수동 | 자동이 기본 |
| 사기업·기타 현직 | `현직 · 회사명` 또는 `현직` | **회사 이메일 도메인 자동**(도메인 → 회사명은 사용자가 입력, 공개 여부 선택). 개인 메일 사용자는 재직 자료 수동 | 자동이 기본 |
| 법인 공식 | `공식 계정` | 운영자 지정, 법인당 1개 | 요청 시 |

원칙: **자동으로 확인되는 것(도메인)은 즉시, 서류가 필요한 것은 수동, 확인 안 된 것은
표시하지 않는다.** 준비생만 예외적으로 자기 선택인데, 이는 자격이 아니라 상태라 위조할
이유가 없다.

## 2. 게시판 구조

처음부터 큰 카페 구조를 흉내내면 빈 게시판이 늘어선다. **글이 자연스럽게 생기는 곳부터**
연다.

| 순서 | 공간 | 성격 | 누가 쓰나 |
|---|---|---|---|
| ① | 공고 댓글 | 공고 하나에 붙는 질문·답 ("마감 연장됐나요", "연봉 협의라는데") | 준비생·합격생 질문, 법인 소속이 답하면 **법인 답변** 강조 |
| ② | 법인 댓글 | 법인 페이지에 붙는 이야기 | 2026-09-09 배포. 명예훼손 위험이 가장 커서 안내 문구가 그 위험을 먼저 말한다 |
| ③ | 게시판 — 채용·이직 | 수습 채용 시즌 질문, 이직 | 셋 다 |
| ③ | 게시판 — 시험·수험 | 1·2차 준비, 합격 후기 | 준비생 중심, 합격생이 답 |
| ③ | 게시판 — 현직 이야기 | 감사 시즌, 사기업 이직, 개업 | 현직자. **인증 회원만 글쓰기** 옵션 고려 |
| ③ | 게시판 — 자유 | 잡담 | 셋 다 |

게시판은 **글 + 댓글 + 추천 + 카테고리(태그)** 단일 모델로 만들고, 위 넷은 카테고리다.

**추천·베스트 규칙(운영자 결정 2026-09-09).** 글과 댓글 모두 추천이 있다(한 사람 한 번, 취소 가능,
비추천 없음). 댓글 베스트는 공고·법인 댓글과 같은 규칙 — 추천 10개 이상인 원댓글 중 많은 순 3개를
상단 고정(`web/comments.js` 의 `BEST_MIN`·`BEST_MAX`). 글도 같은 기준으로 "베스트" 표시·정렬을 둔다
(`post_votes` 테이블, `posts.vote_count` 트리거 — `comment_votes` 와 같은 모양). 댓글은 한 단계 대댓글.
공고 댓글과 법인 댓글도 같은 댓글 테이블을 쓰되 `target_type`(posting/firm/post)만 다르다.
테이블 하나로 신고·임시조치·운영자 삭제가 한 곳에서 처리된다.

### 운영 도구 (댓글을 열기 전에 반드시)
- 운영자 역할: 어떤 글이든 숨김·삭제·복원
- 신고 버튼 → `reports` 테이블 → 자동 임시조치(비공개) → 운영자 처리 → 양쪽에 메일 통지 (약관 §7)
- 첫 달은 **모든 글이 운영자에게 메일로 온다**(양이 적을 때 문화가 정해진다)
- 금칙어·연락처 패턴(전화번호·이메일) 자동 가림 — 담당자 연락처 유출 방지

## 3. 데이터 모델 (Supabase)

```
profiles          user_id(auth) · nickname(unique) · kind(준비생/합격생/현직) · cohort(기수) ·
                  firm_id · company_name · badges(jsonb) · deleted_at
verifications     id · user_id · type(합격/등록/재직) · status · submitted_at · reviewed_at ·
                  file_path(비공개 버킷, 심사 후 null) · reviewer_note
posts             id · author_id · category · title · body · status(visible/hidden/removed) ·
                  created_at · edited_at · vote_count
post_votes        post_id · voter_id · created_at        -- comment_votes(010) 와 같은 규칙
comment_votes     comment_id · voter_id · created_at     -- 010 에서 배포
comments          id · author_id · target_type(posting/firm/post) · target_id(text) ·
                  parent_id(한 단계) · body · status · vote_count · created_at
reports           id · reporter_id · target(type,id) · reason · status · acted_at
firm_domains      firm_id · domain          -- 법인 소속 자동 인증
```

- RLS: 읽기는 공개(visible만), 쓰기는 본인, 삭제·숨김은 운영자 역할
- 탈퇴: `profiles.deleted_at` 기록 + 이메일·인증정보 삭제 + auth 사용자 삭제, `author_id` 는
  남기되 화면에서 "탈퇴한 사용자"로 표시 (약관 §10)
- 인증 파일: Storage 비공개 버킷, 심사 완료 즉시 삭제, 7일 자동 삭제 (약관 §5)

## 4. 로그인

- Supabase Auth 한 곳. 구글·카카오·이메일+비밀번호는 내장, **네이버는 Pages Function 커스텀**
  (OAuth 코드 교환 → 이메일 확인 → Admin API 로 계정 생성/연결 → 세션)
- 같은 이메일이면 어느 버튼이든 같은 계정
- 이메일이 안 오는 로그인(카카오 동의 거부 등)은 **첫 로그인 직후 이메일 입력·확인**을 요구
  (탈퇴·신고 통지·알림이 전부 이메일에 기댄다) — *운영자 확답 대기*
- 카카오 이메일 동의는 **개인 개발자 비즈 앱 전환**(본인인증, 사업자 불필요)이 필요
- 운영자가 만들 것: Google OAuth 클라이언트, Kakao 앱(+비즈 앱), Naver 앱(+검수), Supabase 리디렉션 설정

## 5. 자소서 기능 (Phase 7)

### 재료 → 생성 → 다듬기, 세 층으로

**재료(사용자가 한 번 정리)** — `look/면접컨설팅_0회차_준비시트.xlsx` 의 네 시트를 그대로
데이터 모델로 옮긴다. 시트의 열이 곧 필드다.

| 시트 | 필드 (시트 열 그대로) |
|---|---|
| 01 경험 카드 | 우선순위 · 제목 · 분류 · 내용(상황→행동→결과→느낀 점) · 수치·구체화 포인트 · 메모 |
| 02 페르소나 | 후보 · 한 줄 페르소나 · 왜 이렇게 정의하는가 · 이를 보여주는 경험·근거 · 최종 여부 |
| 03 차별화 포인트 | 우선순위 · 유형(강점/특이 경험) · 내용 · 왜 차별화되는가 · 증명할 경험·근거 · 법인·직무 연결 |
| 04 핵심 질문 24 | No. · 구분 · 질문 · 나의 생각 · 그렇게 생각하는 이유 · 연결할 경험·근거 · 작성상태 |

핵심 질문 24개는 시트에 들어 있다(부록). 구분은 자기이해·지원동기·직무·가치제공·경험·협업·
업무태도·회계업계·AI·시사·커리어·감사직무·산업이다. **3~6번(왜 이 법인·본부·직무, 하고 싶은
업무)은 법인마다 답이 달라지는 질문**이라 "법인 맞춤 생성"이 채워 넣는 자리이고, 나머지는 한 번
써 두면 재사용된다. 경험 카드의 `분류` 와 질문의 `연결할 경험` 이 자소서 문단을 조립하는 연결
고리다.

**생성** — 두 입구.
1. **자유양식**: 재료 전체 + 분량(예: 1,000자) + 톤을 주고 초안 생성
2. **법인 맞춤**: 법인 선택 → (a) 그 법인 공고의 **제출 요건**(자소서 필수/선택, 지정 양식·항목,
   분량, 접수 방법), (b) 법인 페이지의 사실(규모·부문 구성·수습 규모·감사 고객)을 함께 넣어
   "왜 이 법인인가"가 사실에 근거하게 생성
3. **가져와서 변형**: 기존 자소서를 붙이면 재료로 분해해 저장하고, 위 두 입구로 다시 생성

**다듬기** — 저장(버전), 편집, **분량 표시**(자·바이트·공백 포함/제외 — 법인이 "1,000자 이내"
라고 하면 그 기준), **맞춤법 검사**(외부 API 또는 모델 기반, 결과는 제안으로만), 법인별 사본.

### 현실 확인 — "양식"은 거의 없다
대상 공고 31건의 본문을 세어 보면 **자유양식 17건, 자기소개서 언급 22건 중 '선택 제출' 15건,
지정 양식을 암시하는 문구 0건, 이메일 접수 26건**이다. 로컬 법인은 대부분 자유양식이다. 따라서
"법인 양식 엔진"이 아니라 **"공고별 제출 요건 정리"**가 핵심이다:
- 크롤러가 본문에서 `제출서류 · 자소서 필수/선택 · 분량 · 접수 방법(이메일) · 지정 항목`을 뽑아
  `postings.application_requirements(jsonb)` 에 넣는다 (규칙 기반 + 모델 보정)
- 한공회 상세 페이지에 **첨부파일 영역**이 있다(`fn_downloadFile`). 지정 양식(hwp/doc)이
  붙은 공고는 첨부 파일명을 기록하고 상세 페이지에 "지정 양식 있음"으로 표시한다. 파일 자체를
  받아 항목을 해석하는 것은 그다음 단계
- 공고 상세 페이지에 **"지원 요건" 블록**을 먼저 붙인다 — 자소서 기능 전에 그 자체로 유용하다

### 지원 가이드 FAQ 의 반영 (`docs/apply-guide.md`)
- 10~15곳에 내야 면접 1번 → 자소서 기능의 가치는 **빠른 변형**이다. 법인 하나에 한 편을 완성하는
  도구가 아니라, 한 번 정리한 재료로 열 곳에 빨리 내는 도구
- "빨리 낼수록 유리" → 새 공고 알림 메일에서 **"이 공고용 자소서 만들기"** 한 번으로 이어지게
- 끌올은 대부분 끌어올리기 → "이미 지원했으면 다시 보내지 않아도 된다"를 상세 페이지 끌올 배지 옆에
- '채용중'은 믿을 수 없다 → 상세의 "게시판 상태" 옆 안내
- 가이드 전체를 **`/guide` 페이지**로 게시 — 검색 유입과 게시판 첫 글의 재료

### 비용·기술
- 생성은 서버(Pages Function)에서 모델 호출, 사용자 재료는 사용자 소유(RLS). 자소서는 개인정보
  덩어리(경험·학교·이름이 섞인다) → **방침에 별도 항목**, 삭제 시 즉시 파기, 모델 학습 미사용 명시
- 맞춤법: 국립국어원 계열 공개 API 는 상업 이용 제약이 있어 확인 필요. 대안은 모델 기반 교정 제안
- 분량 계산은 클라이언트에서 즉시

## 6. 순서 (제안)

```
③ 로그인 + 프로필 + 닉네임 + 도메인 뱃지(법인·현직)   ← 운영자 앱 설정 뒤 착수
④ 공고 댓글 + 신고·임시조치 + 운영자 도구 + 방침 제6판
⑤ 합격자·회계사 인증(수동 심사 흐름)
⑥ 게시판(채용·시험·현직·자유) — 댓글 모델 재사용
⑦ 법인 댓글
⑧ 공고 '지원 요건' 블록 + /guide 페이지        ← 자소서의 전제, 로그인 불필요라 ③과 병행 가능
⑨ 자소서: 재료 → 자유양식 → 법인 맞춤 → 가져오기
```

⑧은 로그인과 무관해 지금 바로 할 수 있고, 자소서(⑨)의 전제다.
